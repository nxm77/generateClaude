Context architecture

企业AI编程的六层知识上下文

不同知识应该采用不同加载方式：代码索引与文档按需检索，Rules稳定加载，Skills和SOP按任务触发，工具通过MCP或插件调用。

检索型知识

代码索引、API文档、架构说明、业务规则和历史故障。特点是体量大、按需召回、必须提供来源。

约束型知识

编码规范、分层边界、安全禁止项和依赖规则。特点是短、明确、可验证，适合Rules。

执行型知识

开发、迁移、测试、评审和发布步骤。特点是有条件、有顺序、有产物，适合Skills和SOP。

阿阿里巴巴

Qoder CN：文档RAG与代码库检索“双知识源”

Qoder CN可在IDE中使用企业知识库回答问题，也可把企业代码库向量化后用于代码生成和补全。[1][2][4] Repo Wiki进一步自动生成结构化项目文档并跟踪Git增量变化。[3]

双RAG文档回答“应该怎么做”，代码回答“过去怎么做”

公开能力

  • 知识库可设置成员可见范围，并作为IDE问答上下文。[1]
  • 企业代码库处理为可检索向量，用于生成贴近内部代码模式的内容。[2]
  • Repo Wiki为项目形成自动化认知层，当前公开限制为每项目最多1万个文件。[3]

工程价值

  • 适合同时拥有成熟技术文档和公共代码资产的企业。
  • 可用于内部API问答、规范化代码生成、遗留代码理解和新人上手。
  • 需要保证文档库、Git仓库、上传代码和Repo Wiki的版本一致。

突出优势

项目Wiki自动生成能力强，文档和代码两类知识边界清晰。

治理重点

代码压缩包或离线库必须自动增量更新；避免长期使用过期代码知识。
腾腾讯

CodeBuddy / WorkBuddy：可组合的企业RAG上下文

腾讯云当前文档中，企业能力以WorkBuddy Enterprise呈现。企业可创建文档、压缩包和离线代码库知识库；Craft任务可同时组合文件、Git、知识库、终端和Rules。[5][6]

可组合显式选择知识域，并把规范、代码和工具放进同一任务

公开能力

  • 支持按成员管理知识库可见范围和多种文件形态。[5]
  • Rules用于项目级规范，全局提示词用于企业统一命名、注释和代码结构。[7][8]
  • Craft可自主完成多文件修改并展示diff，适合从问答进入任务执行。[6]

工程价值

  • 知识域边界清晰时，可按任务组合后端、前端、安全和API知识库。
  • 企业管理后台便于集中配置知识和规范。
  • 腾讯公开材料称CodeBuddy已在内部大规模应用，但效率数据为厂商自报。[20]

突出优势

企业管理、知识库选择、Rules和多文件Agent结合直接。

治理重点

离线代码库需要自动同步；全局提示词过长会挤占上下文并产生规则冲突。
字字节跳动

TRAE企业版：知识库进入完整“上下文工程”

TRAE企业版把企业知识库、Rules、Skills、智能体、MCP、模型、安全和效能看板放在统一体系。[9][11] 公开发布材料称支持10万文件、1.5亿行代码的仓库索引，并经过字节内部业务验证；相关覆盖和提效数字属于企业自报。[10]

上下文工程知识不仅被检索，还与Agent、工具和组织治理共同配置

公开能力

  • 企业文档集用于沉淀研发规范、技术文档和最佳实践。[9]
  • Skills以SKILL.md封装工作流、知识、脚本和模板，并按任务加载。[11]
  • MCP、CLI、IDE和企业智能体把知识延伸到CI/CD和DevOps。

工程价值

  • 适合超大仓库、复杂工具链和端到端Agent任务。
  • 不仅管理“模型调用”，还跟踪AI生成率、成员活跃和费用。
  • 公开产品数据较强，但对字节内部具体知识库数量和知识治理流程披露有限。

突出优势

大仓索引、Rules、Skills、MCP和企业治理形成一体化平台。

治理重点

规则、技能和Agent资产数量增长后，必须建立Owner、版本、评测和下线机制。
百百度

Comate：代码自动转Wiki，再回流为研发知识

Comate知识集可保存企业文档；DeepWiki把代码库结构、业务逻辑和技术实现自动沉淀为团队Wiki。[12][13] Skills则把脚本、模板、参考资料和任务步骤封装成可版本控制的能力包。[14]

知识飞轮代码 → DeepWiki → 知识集 → Agent → 代码变更

公开能力

  • 知识集可用于问答和续写，并能指定具体文档作为上下文。[12]
  • DeepWiki降低遗留项目文档缺失带来的认知成本。[13]
  • Skills支持按需加载、脚本执行和版本控制。[14]

工程价值

  • 适合历史项目多、文档不完整、需要自动建立项目知识的企业。
  • 专用检索Agent可先浏览知识目录，再逐步读取相关资料。
  • 百度公开称每天新增代码中Comate生成占比超过40%，为官方自报口径。[15]

突出优势

项目知识自动生成与再利用闭环完整，Rules和Skills工程化程度高。

治理重点

自动Wiki必须支持人工校正、来源行号、版本追踪和变更后及时更新。
美美团

美团：把隐性经验转成Rule、Skill、SOP和门禁

美团早期Rome实践已让IDE根据开发内容主动匹配内部知识文档和风险信息。[16] 2026年的31万行代码重构案例进一步把团队共识固化为Rule、Skill、重构SOP和Pre-PR检查。[17]

可执行知识重点不是“AI读过资料”，而是“AI必须按规则完成并被验证”

公开能力与实践

  • 内部知识可在编码现场主动推荐，而非等待开发者搜索。[16]
  • 重构案例中，团队先统一架构和职责，再将共识写成AI Rules。[17]
  • 复杂迁移由核心人员先做样板，再沉淀为AI可执行SOP；提交前用Pre-PR多轮自查。

工程价值

  • 适合存量系统、技术债重构和高比例AI生成代码的团队。
  • CatPaw公开支持知识库、提示词、工具和企业Agent托管。[19]
  • 官方披露内部研发渗透率和代码生成率，但属于企业自报数据。[18]

突出优势

把知识从“检索材料”提升为强制规则、任务方法和质量门禁。

治理重点

必须先有人形成正确共识；错误或过时的Rule/SOP会被AI规模化放大。
Task pipeline

一次企业级AI编程任务，应如何使用知识

以下流程综合五家公司公开实践，体现知识从“检索”走向“执行与验证”。

01 识别任务

读取需求、Issue、当前分支和变更范围，确定涉及的模块、规范和业务知识域。

02 建立项目认知

通过代码索引、Repo Wiki或DeepWiki理解目录、调用关系、数据模型和相关测试。

03 检索企业知识

按权限检索API、架构、业务规则、故障经验和安全要求，并保留引用来源。

04 加载约束与技能

稳定加载项目Rules，按任务调用开发、迁移、测试或评审Skill/SOP。

05 执行与工具调用

修改代码，调用构建、测试、静态扫描、日志和CI工具，持续根据结果修正。

06 Pre-PR验证

检查架构边界、异常、安全、性能、测试覆盖和影响范围，生成可追溯报告供人工复核。

关键原则：业务语义和风险边界由人确定；AI负责穷举分析、生成、执行和自查。知识库不能替代资深工程师形成正确规则。
Knowledge asset design

五类研发知识资产应分开治理

01 Code Index

代码索引库

源码、符号、调用关系、Git历史、依赖、测试。必须增量更新。

02 Docs RAG

技术文档库

架构、API、中间件、故障、平台手册。按需检索并引用来源。

03 Rules

项目规则

分层、依赖、命名、安全、日志和禁止项。短且可检查。

04 Skills / SOP

任务能力包

开发、迁移、测试、评审、发布。按任务渐进加载。

05 Business

业务知识库

术语、流程、状态机、数据定义和历史决策，由业务专家共同维护。

Implementation blueprint

大型企业落地建议

从试点到规模化，优先建设可验证的知识资产，而不是一次性上传所有资料。

推荐实施顺序

  1. 选择一个边界清晰、测试较完整的项目做试点。
  2. 建立增量代码索引，排除构建产物、第三方库和重复代码。
  3. 梳理20—50条高价值Rules，而非一次写数百条规范。
  4. 选择3—5个高频任务沉淀Skills/SOP，例如Bug修复、单测、Code Review。
  5. 接入构建、测试、扫描和Issue系统，实现“能执行、可验证”。
  6. 记录命中知识、来源、采纳、返工和缺陷，持续优化。

必须设置的安全边界

  • 知识检索继承人员和项目权限。
  • 敏感代码发送模型前执行拦截或脱敏。
  • AI不得自动提交、推送、合并或发布，除非企业明确授权并有审批门禁。
  • Rule、Skill、MCP和Agent必须有Owner、版本、审计和下线流程。
  • 生成代码必须经过测试、静态扫描和人工业务语义复核。

适合衡量的指标

效果采纳率

生成内容最终被采用的比例，区分补全、Agent和评审建议。

质量返工与缺陷

AI代码返工率、缺陷密度、评审发现和线上回滚。

知识命中与过期

知识命中率、无答案率、过期引用率和人工纠错闭环。

Risk map

常见失败模式

把所有资料塞进一个库

导致知识域混乱、召回噪声、权限难以拆分。应按技术、业务、项目和安全域分库。

只做RAG，不做规则和验证

AI“看过文档”并不意味着会稳定遵守。强制约束必须转成Rules和自动检查。

代码库不增量更新

离线压缩包很快失效，AI会生成已废弃API和旧架构代码。

规则未经团队共识

错误Rule会被AI高频复制，技术债被规模化放大。

没有来源和审计

无法判断AI为什么这样生成，也无法定位错误知识和责任边界。

用生成率替代质量

AI代码比例高不等于价值高，应同时观察交付周期、缺陷、返工和维护成本。
